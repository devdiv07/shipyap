# Initial security model — Phase 0

## Assets
Social publisher token (future), private research source files (future), approved content and destination, user identity (future), logs and credentials, public reputation.

## Threats and controls
| Threat | Current or required control |
| --- | --- |
| Malicious README instructs AI to leak secrets | Ingestion is data-only. The only ingestion (`ingest-github`) writes retrieved bytes verbatim and never executes, imports, parses or renders them (an AST test forbids process, `eval`/`exec` and environment access in `ingestion/`); no publisher is connected. `draft-model` (Assignment 04) sends snapshot text to a model only as data inside the brief; the model has no tools, receives no credential, and its reply is checked like any drafter's (see the model-drafting rows) |
| Drafter accesses Buffer token | The drafting and publication packages cannot import each other (test); only `publication/buffer.py` reads `PROS_BUFFER_API_KEY`, and no other module may even name it (test). The key is held as a `SecretStr`, sent only as an `Authorization` header to `api.buffer.com`, and never appears in an error, the ledger or output (tests scan stdout, stderr, logs, the database and every file) |
| Forged user approval | `pros review` requires an explicit confirmation of the saved text, destination and time. An opaque server-held ticket binds that confirmation to the session, current bundle, decision sequence and X text; stale or substituted candidates are refused. This is an accident barrier, **not authentication**: anyone with the local session URL or ledger write access can act as the owner. **Content hash is not approval**; READY_FOR_REVIEW is not approval. Scheduling is a separate typed confirmation. |
| Duplicate or unauthorised post | One approval has at most one intent (primary key) and at most one `createPost` request; the intent is committed before the request; nothing is auto-retried or auto-resent, and an interrupted or ambiguous submission is only ever reconciled by reading (PUB-02) |
| Package tampering | Deterministic SHA-256 fingerprint included and unit-tested; future media digest validation |
| Duplicate publishing on timeout | No real publisher; future durable intent, query provider state, UNKNOWN/no blind retry |
| Public claim unsupported | Strict schemas and deterministic checks now; semantic check and human review required later |
| Cross-workspace access | workspace_id in models; NO server auth/tenant isolation. Beta blocked until authz tests pass |
| Secret leaks in logs | No real secrets required; env files ignored. Future masking/scanning and bounded logs |
| Untrusted manifest/claim paths and URLs in `check-evidence` | Portable path policy (traversal, absolute, drive/ADS, reserved device names, trailing dot/space, non-NFC, case collisions) + resolved containment under the designated snapshot root (symlinks/junctions followed, then checked). URLs: HTTPS only, no credentials/query/fragment, never fetched. Rejected values are not echoed. **Residual:** snapshot assumed immutable during a check; identity re-checks narrow but do not eliminate TOCTOU races |
| `check-evidence --out` redirected by directory/link swap (Codex P2-01, reproduced with a Windows junction) | **Precondition:** `--out` and its ancestors are local, operator-controlled directories. Hardening (not a containment guarantee against a malicious concurrent writer): POSIX writes are relative to an `O_DIRECTORY\|O_NOFOLLOW` descriptor (`dir_fd`); Windows pins the directory with a handle lacking `FILE_SHARE_DELETE` (NTFS then refuses renaming it or its ancestors), verifies the handle identity equals the junction-free final path, and creates files through that path. All report files are created with `O_EXCL`. **Residual:** admin/backup-privileged processes, per-session drive-letter remapping, filesystems not enforcing NTFS share/rename rules; POSIX path not executed on the Windows dev host (executed on Linux 2026-10-18). Residual risk accepted by the independent reviewer (Codex) under the precondition above; see `R1-RESIDUAL-01` in `docs/quality/open-issues.md` |
| Ambiguous or smuggled JSON (Codex P2-03: repeated `status` key produced a mechanical PASS) | Claims and manifests decoded once by a strict stdlib decoder: duplicate keys at any depth, NaN/Infinity/non-finite numbers, non-UTF-8 and excessive nesting rejected before strict Pydantic validation (`DUPLICATE_JSON_KEY` / `INVALID_JSON`). Lone surrogate code points (`\ud800`..`\udfff` escapes; Codex R1 P2-02 produced a PASS) are rejected in every key and string at any depth by an iterative walk of the decoded value (`INVALID_UNICODE`, location `<document>`, no content echoed); valid escaped pairs and all other Unicode are accepted. Legacy positional CLI still uses last-wins parsing (tracked) |
| Error paths leaking secrets or local paths (Codex P2-02) | `check-evidence` argument errors never echo values; filesystem metadata/read/write/close/stdout failures become fixed codes on stderr (exit 2) with exception context suppressed; reports contain only fixed messages. Snapshot source descriptors are closed exactly once (never retried); an `OSError` on close after a successful read is `SOURCE_CLOSE_FAILED` (MISSING_SOURCE, never SOURCE_MATCH or PASS), and an earlier read/identity failure stays the primary reason (Codex R1 P2-01). Closed stdout (`ValueError`) or no stdout (`sys.stdout is None`) → `STDOUT_WRITE_FAILED`, exit 2; other `ValueError`s are not reclassified (Codex R1 P3-01). Legacy CLI still prints raw Pydantic validation errors (tracked; must be fixed before confidential or external input) |
| Report used as an authorization input | **Not permitted.** Report-level consistency invariants are incomplete (tracked P3-01); reports are review aids, never approvals. No automated process may treat a mechanical PASS as authenticated approval, or infer a complete `--out` bundle from file existence (partial bundles are possible, tracked OUTPUT-01) |
| GitHub ingestion (`ingest-github`): network, SSRF, redirects, credentials, resource exhaustion | One fixed host (`api.github.com:443`) in one module (`ingestion/transport.py`); request paths are built only from the validated request and 40-hex ids and re-checked against a strict pattern before sending; every 3xx is refused, never followed; no proxy variables, no `Authorization` header and no token or environment read (an AST test forbids network imports outside the transport and process or environment access in `ingestion/`); verifying TLS 1.2+; `Accept-Encoding: identity`; byte caps enforced while streaming, a request budget (20), an idle timeout (10 s) and an overall 60 s deadline enforced on every TCP connect attempt, the TLS handshake and each send and receive (each armed with min(idle, time left); Codex Remediation P2-A); TLS context and connection construction failures are fixed codes (P2-B); zero retries (a rate limit fails with `RATE_LIMITED`). Errors are fixed codes: no URL, response body, path or OS text. **Residual:** DNS resolution (`getaddrinfo`) is not bounded by the deadline; unauthenticated public reads only; TLS/CA or GitHub-side compromise is out of scope; no proxy support |
| GitHub provenance: provider tree metadata and revision pinning | The request must carry a full 40-hex commit id (no branch or tag resolution). The commit, every tree and every blob are requested by id and each response must carry the id that was asked for. Symlink (`120000`), submodule (`160000`) and directory entries are refused before any content is fetched, `truncated` listings fail, and each blob's Git object id is recomputed from the received bytes. **Not proven:** tree listings are provider-supplied metadata; complete tree membership (and that a tree id really hashes to its listing) is not independently verified, and Git object ids are SHA-1. A matching digest shows byte identity with what GitHub served for that id, not authorship, truth or approval |
| `ingest-github` output: partial or replaced snapshots | A NEW directory only: written in a sibling staging directory (completion record last), verified against the completion rule (`writer.verify_completion`: exact file set, no links, sizes and digests match), then published with one `os.rename`; on failure only what the run created is removed. **Residual:** operator-controlled filesystem assumed and checks are best-effort. A concurrent local writer can race the final-name check; on POSIX `rename(2)` replaces an EMPTY directory created in that window (UNVERIFIED, not run on Linux). No cross-platform atomic no-replace guarantee is claimed. The completion record is a consistency indicator that anyone able to write the directory can forge; it is not an attestation, and OUTPUT-01 does not apply to this writer |

| Editorial (`draft-brief` / `draft-build`): untrusted snapshot text steering the drafter or the checker (prompt injection) | Source text is data. The brief marks it untrusted and tells the drafter never to follow it. The tool runs no model and executes nothing; an AST test forbids environment access, dynamic code, direct disk writes and any `publication` import in `editorial/`. Checks are deterministic and do not trust the drafter. Quotes must be located in the pinned lines, and a quote is only a locator: numbers, first-person words and comparison phrases count as evidence only when the real source text inside the located span contains them, with the source's own token boundaries (Codex A03 P2-A, Remediation R1). Digit numbers must appear in the segment's own evidence. Comparisons are detected in the rendered paragraph, so splitting a phrase across segments does not hide it (P2-B). A comparison needs the phrase in the evidence of the segments it spans, whatever their declared basis. Hashtags and links are allow-listed. **Residual:** a drafter that faithfully quotes injected or wrong source text passes the mechanical checks (the words really are there); only the human reading the excerpt in `review.md` catches it. Semantic support stays UNKNOWN |
| Editorial: drafter response as untrusted input | Strict JSON (duplicate keys, NaN, truncation, lone surrogates refused), capped at 512 KiB, frozen strict schema. Control, format and bidi characters are refused in every text field. `brief_sha256` must match the brief. Errors are fixed codes; schema details name known fields only, never values. The `generator` declaration is self-reported and shown as unverified; it proves neither authorship nor edit lineage |
| Editorial: a draft treated as approved | **Not representable.** `review_state` is the literal `UNAPPROVED` in the assertion map and the bundle record. `DraftStatus` has no approval member. Exit 0 means only "no blocking findings". No consumer may treat a draft bundle, its record or its exit code as approval. Approval needs a separate, authenticated process (future) |
| Editorial: modified or mismatched inputs, and partial bundles | The snapshot must pass `verify_completion`, and the bytes used are re-hashed against the record. The brief must pass the bundle completion rule and still match the verified snapshot, including its embedded source lines. Bundles are published through the A02 staging writer (`publish_directory`): O_EXCL, record last, verify, one rename, cleanup of only what the run created. **Residual:** the bundle record is a consistency indicator anyone who can write the directory can forge (same as INGEST-01); the snapshot, not the brief, stays authoritative for source text |
| Editorial: review sheet rendered in a Markdown preview | Every untrusted string is shown in a fenced block or an inline code span whose backtick delimiter is longer than any run inside it, so a preview cannot render injected HTML, links or remote images. Stdout and stderr are ASCII-only |
| Model drafting (`draft-model`): data sent to a third party | Sent per run: the fixed system prompt, the response schema and `brief.md`, which must be byte-identical to the rendering of the verified `brief.json` (a re-hashed, edited `brief.md` is refused). `brief.md` holds public snapshot text plus the contributor's name and unpublished notes. Nothing else is sent: no paths, environment or other credentials. `--dry-run` shows the exact `brief.md` digest and sends nothing. **Residual:** provider retention and use under Anthropic's terms for this organization are UNVERIFIED here (MODEL-01). The product owner must approve sending the brief before any live run |
| Model drafting: API key disclosure or misuse | One variable, `PROS_ANTHROPIC_API_KEY`, read in one function of `drafting/provider.py`; AST tests enforce that it is the only environment read in the tree and the only module naming the variable. The key is held as `SecretStr` and passed explicitly to the SDK, so no credential environment variable, profile, `ant auth` login or Claude Code credential is consulted (verified against anthropic 1.15.0). There is no CLI option for it, and tests prove a sentinel key never appears on stdout or stderr or in a bundle file. Redirects are not followed, so the key header is never re-sent elsewhere. A non-blank `ANTHROPIC_CUSTOM_HEADERS` is refused before any request, because the SDK merges it over the key header (a test demonstrates this). Coding agents must not hold the key |
| Model drafting: runaway or surprise spend | `--max-cost-usd` is required. Before generating, the provider counts the exact request's input tokens (a separate request that generates nothing; any failure stops the run). The estimated maximum is (count × 1.10 + 2,000) input tokens plus 16,000 output tokens (`max_tokens`, which bounds thinking too) at hand-copied list prices; generation is refused if it exceeds the budget. One generation request per run: `max_retries=0`, no refusal fallback, no loop; a timed-out request may already be billed and is not retried. stdout and stderr report usage and an estimated charge, labelled as not a billing guarantee. **Residual:** the allowances and prices are judgement and can go stale (MODEL-03); the only cap across runs is the provider-side workspace spend limit (MODEL-05) |
| Model drafting: SDK behaviour driven by the operator's environment | Fixed `base_url` (ignores `ANTHROPIC_BASE_URL`), explicit timeouts (connect 10 s, read 300 s), SDK tracing and trace propagation off; a non-empty `ANTHROPIC_LOG` is refused before any request (SDK debug logging prints request options, including the brief, to stderr). **Not controlled (MODEL-04):** proxy variables (`HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`) are honoured by the SDK's HTTP client, so an operator-configured proxy can route the request; certificate trust comes from the OS store. A fixed base URL does not stop operator-configured routing |
| Model drafting: model reply as untrusted input (including prompt injection from source text) | The model gets no tools, only text in and text out. The reply must end with `end_turn` (refusal, truncation, other stop reasons and anything but one text block are refused) and must be strict JSON (duplicate keys, NaN and lone surrogates refused) holding only the four editorial fields. The model cannot set `brief_sha256`, `response_version` or `generator`; the tool adds them. The bytes then go through the unchanged A03 path: strict parser, caps, schema, grounding checks, staged publication. Provider errors are fixed codes; SDK messages and response bodies are never shown. **Residual:** as EDIT-01 — a model that faithfully quotes injected or wrong source text passes the mechanical checks; only human review catches it |
| Model drafting: model text treated as verified or approved | Not representable: the bundle is the A03 draft bundle (UNAPPROVED literal, semantic support UNKNOWN). The `generator` label (model, prompt version, request id) is self-declared and unverified, like any drafter's. Exit 0 means only "no blocking findings". `draft-model` imports nothing from `publication` (AST test) |

## Invariants
- Never publish from code-generation process.
- No credentials in model prompts.
- Approval of exact bytes + authenticated actor before any real write.
- Unknown provider create result must not be blindly retried.
- Kill switch must stop new creates; already-scheduled posts require provider cancellation/pause.

## Failure to trust
An agent instruction, `.claude/settings.json`, repo ownership field, or sha256 alone is **not** a hardened security boundary. Enforcement belongs in independently tested application logic and runtime permissions.
